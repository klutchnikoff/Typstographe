# Continuous typing responsiveness — 5 November 2026

The production preview now prepares detached pages in short CPU slices, yielding
full browser tasks between slices and cancelling obsolete work. All pages still
publish atomically with one revision. Abandoned/replaced canvases are explicitly
released; navigation retains lightweight revision/page metadata instead of the
whole RGBA packet. The existing latest-only compile queue is unchanged, with no
fixed 500–600 ms typing debounce and no parallel compilation backlog.

## Verified native result

Before `dae6c9c`, production correction `4d4af70`. Actual release Tauri/WebKit,
production full RGBA, same 2/7/24-page Articles and fixed input strings, on
Apple M1 Max (32 GiB), macOS kernel 25.6.0, Rust 1.98.1. Twelve sessions per
variant: two fresh processes per size and preview on/off mode,
reversed mode order on the second pass. Both compiled core and frontend stamps
match their manifests. No builds or functional test runners ran during timing.

An independent worker schedules native WebKit `insertText` operations every
100 ms and then every 250 ms, 24 characters per phase. Excluding the first two
inputs gives **44 samples per cell**. This measures the WebKit editing pipeline,
not physical keyboard/IME delivery or physical GPU presentation.

24-page Article, preview updating, **250 ms per character**:

| Measurement | Before | After |
| --- | ---: | ---: |
| Worker message → main-thread handler, p95 | 25 ms | 3 ms |
| Scheduled input → next animation-frame opportunity, p95 | 40 ms | 21 ms |
| Scheduled input → two frame opportunities, p95 | 51 ms | 36 ms |
| Frame gap, p95 | 78 ms | 44 ms |
| Largest observed frame gap | 123 ms | 67 ms |

The native edit call itself remains ~1 ms p95 in this case. The significant
delay was waiting to run while preview preparation chained page uploads in one
task. Each individual upload was short (at most 4 ms before); 24 in succession
monopolized the interface. After correction the single-upload maximum is 6 ms,
but the interface gets task boundaries instead of waiting for every page.

This gain does not come from disabling preview updates: across the two long-
Article 250 ms phases there are **44 atomic publications after versus 46 before**,
and 1,099 page uploads versus 1,104. Partial preparations can now stop when an
edit makes them obsolete. The confirmed final preview is identical.

Smaller Articles, preview on, 250 ms cadence (p95):

| Pages | Input queue, before → after | Next frame, before → after | Frame gap, before → after |
| --- | ---: | ---: | ---: |
| 2 | 2 → 1 ms | 26 → 24 ms | 27 → 24 ms |
| 7 | ~0 → ~0 ms | 21 → 21 ms | 35 → 25 ms |
| 24 | 25 → 3 ms | 40 → 21 ms | 78 → 44 ms |

The unchanged off-mode control is close between variants. On the long Article
at 250 ms, input queue p95 is 2 → 1 ms and next-frame p95 is 34 → 32 ms.
Frame alignment explains why preview-on next-frame times can be lower than
off-mode times: this is not evidence that enabling preview accelerates editing.

## Remaining interruptions and scope

There is no claim of eliminating every stall. At **100 ms cadence on 24 pages**,
the preview publishes no intermediate frame in either variant: compilation
results become obsolete during typing. Input-to-next-frame p95 stays at 17 ms,
but the two-frame p95 goes from 35 to 80 ms (maximum 88 → 100 ms), and the
largest frame gap goes from 71 to 80 ms. These pauses occur without canvas
uploads in the measured input phase; this experiment does not isolate their
cause. They must not be attributed to the removed synchronous upload loop or
silently omitted. Background rendering/common work still warrants investigation
if it remains perceptible in manual use.

Worker timer lateness is typically 3–5 ms median and 5–6 ms p95 in both variants.
The input-queue metric starts at actual worker send time; the frame metrics
start at the scheduled deadline and include generator jitter. Millisecond clock
resolution produces occasional tiny negative queue estimates in the raw data.
Raw values are retained; displayed whole-millisecond values are rounded.

Only two fresh processes and 44 warm input samples per cell are available.
Series run successively, not randomly interleaved. Frame samples include warm-up
and are numerous within a session but not independent process repetitions.
These are distributions on this Mac, not hard responsiveness budgets or
Windows/Linux timing claims. No new physical keyboard, IME, scrolling, memory
or GPU-presentation qualification is claimed. The production renderer/protocol
and Typst compilation are unchanged.

## Preservation and checks

- All **1,152 native input events** (576 per variant) are preserved in order and
  confirmed by the document engine; the browser reports trusted input events.
  These are generated by its native editing API, not by physical keystrokes.
- All 24 accepted sessions pass their compiled core/frontend checks and final
  text, selection, source, pixel and navigation checks. Six cohorts (size/run)
  each compare preview-on/off before/after against the same final state.
- The production build, formatting, 459 Vitest tests and 14 Chromium/WebKit
  functional cases pass. New tests cover full-task yields, sliced preparation,
  atomic publication, invalidation, partial-upload failure, resource release and
  closure. Existing reference and backward-navigation paths pass.
- Native-locale script tests pass. The Vite watcher test times out in the
  sandbox and succeeds on its isolated rerun outside it; no watcher code changes.
- Existing local projects and unrelated branding work are not modified by the
  recipes or included in these commits.

## Excluded attempts and validation correction

Some after attempts failed before input while macOS showed `loginwindow` after
sleep. They are excluded. A read-only AppKit preflight now refuses a locked
desktop, because DOM visibility alone can still report `visible` there while
animation frames are suspended. Normal visible-window behavior is kept; no
background throttling flag is disabled.

Another after attempt completed its timed input phases but failed the final
pixel check: asynchronous hashing retained a static list of canvases while a
redundant same-revision render replaced and released them. The recipe now waits
and pauses the render queue before hashing, **outside all timed input phases**.
The final after series was rerun in full. Baseline input probes are unchanged;
the validation-only fix also applies when reproducing baseline builds now.
Invalid/incomplete pilots stay only under ignored `output/`.

The build helper invalidates and removes instrumented local release-core
artifacts while retaining third-party caches. Statically linked measurement
binaries remain usable; later production builds recompile their own core.
No screenshot, video, profiler trace or personal project was recorded.
